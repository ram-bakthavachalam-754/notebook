Notebook Family Controls

Let a parent decide what Notebook's AI agent will talk about with each child, from the parent's own Mac or iPhone, while every family member keeps their own private notebook.

Author Ramachandran BakthavachalamDate 19 October 2026Status ProposedApplies to Notebook 0.3 (Mac + iOS)

Main design doc · Prototypes: the grown-up app, the kids app, and the parent's Family controls with a live kid phone. All three run locally.

Grown-up appKids appFamily controls

Summary

Notebook is a local-first app. Each person's notes sync only through their own private iCloud database, encrypted with a key that never leaves their devices. The AI agent runs on each device using a provider key entered on that device.

This design adds one new role, a managed child. A parent creates a profile for each child, chooses which topics the agent may discuss, writes extra rules in plain English, and picks the AI connection. The parent then presses Publish. The child's devices download the signed rules within about 30 seconds and enforce them. The child can't change those settings.

The design rests on one point: the child's AI access arrives only inside the parent's published rules. Removing or bypassing the rules removes the AI along with them.

Goals

Goals

  • A parent controls, per child, what kinds of questions the agent answers, how it answers them, and which tools it may use.
  • A parent can manage all children from either of the parent's own devices, with no server to run.
  • Restrictions are enforced in code and by separate checks. Instructions to the model are an extra layer on top, not the only one.
  • The child's experience stays friendly. A blocked question gets a kind reply the parent wrote, never an error.
  • A partner uses Notebook independently, with no access in either direction.

Non-goals

  • Reading the child's chats or notes. The parent manages settings only. The child's notebook stays in the child's iCloud, as today.
  • Device-wide parental controls. Screen Time remains the tool for blocking other apps, websites and app deletion.
  • A shared family notebook. That could come later and would need its own design.

Each child signs in with their own Apple Account (a Family Sharing child account). The partner needs nothing beyond installing the app through TestFlight or a signed Mac build. Their data already lives in their own private CloudKit database.

The experience

Parent: set up a child

  1. Open Settings → Family → Add a child. Enter a name and age. Notebook applies the starting rules for that age (Under 10, 10–13, or Teen).
  2. Adjust topics, the answer style, your own rules, the refusal message, the AI connection, and tools and time.
  3. Choose Add a device…. On the child's iPhone, scan the QR code from Settings → Join family; on a Mac, paste the code. Both screens show a 6-digit number to compare.
  4. Press Publish to [name]. Each device row changes from "Updating to v8…" to "Up to date · v8".

Edits are drafts until published, and the sidebar shows a count of unpublished changes for each child. Child profiles are saved in the parent's own notebook, so they sync between the parent's Mac and iPhone through the existing encrypted sync.

Child: using the agent

The rules are invisible to the child. Nothing on the child's devices lists topics, rules, versions or who set them.

  • A friendlier agent screen: rounded type, larger text, starter questions, and the child's own color.
  • A blocked question gets the parent's refusal message as an ordinary reply, with no label naming a rule or topic. Careful topics are simply answered at the child's level.
  • Agent settings show one line, "A parent set up your AI on this device", with nothing to change. The provider, model and key are never shown.
  • Updates arrive silently. A counter shows the questions left today.
  • Live typing is off. Each reply appears once it has passed the answer check.

Which apps a child gets

How apps are hidden

  • Mac: js/core/app-manager.js skips routes, title-bar switches and keyboard shortcuts (Cmd+1–4) for apps that are off. The main process also rejects store reads and writes for their keys, so a hidden app can't be reached through the developer tools.
  • iOS: NotebookViews.swift builds the tab bar from the policy. The model refuses edits to hidden collections.
  • Agent: the collections of a hidden app are removed from notebook_schema and every record tool. With Money on in savings mode, the agent can read goals and allowance but gets no finance_summary.
  • Data: turning an app off hides it but never deletes anything. Turning it back on brings the data back.

What a parent controls in the agent

Topics

Ask is for curiosity

Kids don't need AI for homework. Ask exists to answer the questions children wonder about and to make them want to learn more. Asked to do homework ("do my worksheet", "write my essay"), it gives a fixed, friendly reply offering to explain the idea instead. The question check catches these before the AI is called.

  • Starter prompts spark curiosity across subjects: space ("How far away is the Moon?", "What's inside a black hole?"), Earth ("Why do volcanoes erupt?"), history ("Who built the pyramids?"), math ("Why is zero so important?") and nature ("How do bees make honey?"). Each is labeled with its subject.
  • Wonder of the day shows one new question each day, and Surprise me asks a random one.
  • Follow-up questions. Every answer ends with two suggested follow-ups as buttons, so one question leads to the next.
  • Photos are for showing something they're curious about: a bug, a leaf, the Moon.

How Ask answers

  • Short and simple: one or two sentences, no follow-ups.
  • Explain and wonder (default): explains at the child's age, then offers follow-up questions.
  • Guess first: asks the child to guess, then explains when they tap "Tell me!".

Your own rules

Free-text rules such as "No video game cheats or hacks" or "No celebrity gossip". Each rule is checked on every question and every answer. Rules that change the style of an answer (for example "Answer in Tamil when asked") go into the AI's instructions instead of blocking anything. A rule is at most 160 characters, and a child can have up to 20.

Also per child

  • Refusal message: what the child sees for a blocked question, at most 200 characters.
  • AI connection: provider, model and API key. Use one key per child with a monthly spending cap set at the provider. The model must accept images, because attached photos are checked too.
  • Photos & files in chat: take a photo (iPhone), choose from photos, attach files (iPhone and Mac). Attachments are checked with the question.
  • Tools: web browsing, and editing notes and journal.
  • Time: messages per day and quiet hours.

How questions are checked

A system prompt alone is easy to talk around, so every child question passes through three layers, plus tool restrictions enforced in code.

Child asksDaily limit and quiet hours checked locally first
→
1 · Question checkSmall model call with only the rules and the question. Returns a decision and a reason.
→
2 · Agent runNormal agent loop. The rules are added to its instructions and blocked tools are removed.
→
3 · Answer checkFinal reply checked against the same rules before it's shown
→
ShownReply, or the parent's refusal message
Blocked at step 1: the parent's message is shown and no agent call is made.
Crisis at step 1: a fixed caring reply with help resources, whatever the topic settings.
Fails at step 3: the reply is replaced with the refusal message and only the notice is stored.

The check call

The checker is a separate request with no conversation history and no tools. It receives only the published rules, the child's age, and the text to judge, which keeps "ignore your rules" attempts in the chat from reaching it. It must return strict JSON:

{ "decision": "allow" | "careful" | "block" | "crisis",
  "topic": "scary",
  "rule": null | 0,                 // index of the parent's rule that matched
  "reason": "Asks for the scariest horror film" }
  • Fail closed. If the check can't run (network error, invalid JSON, timeout after 20 seconds), the question isn't answered. The child sees "I couldn't check that question. Try again in a moment."
  • Higher setting wins. When a question touches several topics, the strictest setting applies, and a matching parent rule always blocks.
  • Cost. Two short extra calls per question, typically a few hundred tokens each, on the same provider and key.
  • Context. For short follow-ups like "why?" or "more", the checker also receives the previous question so it can judge what's meant.

Enforced in code

  • Tool filtering. Blocked tools are removed from the request, and AgentCore.execute rejects them if the model calls them anyway. This is the same pattern read-only mode already uses (js/agent/agent-core.js:213, :124).
  • Hidden collections. With Finance off, finance collections and finance_summary are removed from the agent's tools.
  • Web pages. Text read from web pages is covered by the answer check, because everything the child sees passes through step 3.
  • Settings lock. The provider and key come only from the rules, and the rules themselves are never passed to the child-facing UI. The settings IPC (agent-configure) and the iOS saveSettings refuse changes while a policy is installed.

Why the public database

CloudKit sharing (CKShare) would also work, but the child has to accept each share through the system's share flow. Notebook's Mac sync runs in a helper app that Electron starts, which doesn't receive those share callbacks. A public-database record that only its creator can write, holding signed and encrypted data, gives the same guarantees with one fetch by record ID. It also needs no new entitlements beyond the existing container.

Update, 19 October 2026: the Mac app is now native SwiftUI and links NotebookCore directly, so it can receive share callbacks. The public-database design still stands, because it needs no acceptance step on the child's device.

Record format

// recordType FamilyPolicy, recordName = random 128-bit policy id
envelope   = AES-GCM(familyKey, policyJSON, aad: policyID ‖ version)
signature  = Ed25519.sign(parentKey, policyID ‖ version ‖ envelope)
fields     = { envelope: Bytes, signature: Bytes, version: Int64 }
  • Enrollment. The QR code or pasted code carries the policy ID, the family key, the parent's public key and a one-time secret. It reuses the existing pairing flow: ECDH, a 10-minute expiry and a 6-digit confirmation (SyncSecurity.swift, CloudSync.beginPairing).
  • Verification on the device. The child's device checks the signature against the enrolled public key and refuses any version lower than or equal to the one installed. The policy then goes into the device's local store, so it keeps working offline.
  • Removing a device. Rotate the family key and publish. Every device still enrolled gets the new key, which is sealed separately to each enrolled device's public key.
  • Leaving kid mode. Only a policy the parent publishes with "managed": false releases the device. There is no local switch.

What a kid could try

AttemptResult
Change agent settingsSettings are locked. The provider and key come from the rules, and both runtimes refuse configuration changes.
Talk the agent out of its rules ("pretend you're allowed")The question check runs separately without the chat history, and the answer check judges the output regardless of how it was produced.
Delete and reinstall the appA fresh, unmanaged install has no AI key and therefore no agent. On iOS, Screen Time can also block deleting apps.
Use their own API key in a reinstalled copyPossible for a determined teen. Screen Time and the conversation are the real answers here.
Extract the key from a MacHard (it's in safeStorage) but possible for a technical kid. That's why each child gets a separate key with a spending cap, which you can revoke at the provider.
Replay an older, looser policyRefused, because the version must increase. Only the parent's account can write the record anyway.
Stay offline to avoid an updateThe last installed rules keep applying. With no network there's no AI either.
Change the device clock to skip quiet hoursPossible on Mac. Fine for now. A future version could use the provider response's Date header.

Build order

1

Rules and checks

agent-policy.js, enforcement in both runtimes, and a hidden debug option to install a policy file by hand. This alone delivers the core behavior on one device.

2

Parent's Family editor

Mac and iOS screens matching the prototype. Profiles saved in the parent's notebook, with drafts and a count of unpublished changes.

3

Delivery and enrollment

FamilyPolicy record, signing and encryption, QR and paste enrollment, fetch on the sync timer, locked kid settings, device status rows.

4

Release

Docs, CloudKit Production schema, TestFlight for the partner and children, Developer ID notarized Mac build.

Testing

  • Node tests (npm test): presets, check parsing (invalid JSON fails closed), strictest-setting logic, tool filtering and rejection, settings lock, daily limit.
  • Native tests (npm run test:native): signature and encryption round trips, version rollback refused, a tampered envelope refused, enrollment-code expiry.
  • Question set: a fixed list of about 150 child-style questions with expected decisions for each preset, run against the real checker model. It doubles as a regression suite when the model changes.
  • On devices: a signed parent Mac and a child iPhone on separate Apple Accounts. Check publish-to-update time, offline behavior and an iCloud account change.

Open questions

  • Blocked-question summary for the parent. Out of scope for now. A weekly count of blocked questions by topic, with no question text, would help tune the rules without reading the child's chats.
  • Asking for an exception. Should a child be able to tap "Ask Dad" on a blocked reply, sending a request without the question text?
  • Checker model choice. The same model is the simplest option. A cheaper dedicated checker model would cut cost but adds a setting.
  • Parent name. "Dad" is set per family. Two organizers (both parents managing) would need a second signing key on the policy.
