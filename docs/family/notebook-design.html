Notebook Design

Notebook is a private, local-first notebook for one household: notes, a journal, personal finance, saved links and an AI agent, on Mac and iPhone. This document reviews how the app is built today and describes every feature we've designed for it: family controls, a kids' version, photo and file attachments, sharing, and the new Links section.

Author Ramachandran BakthavachalamDate 19 October 2026Status ProposedCurrent version Notebook 0.2.3Updated 19 October 2026: native Mac app, Documents, Links

Prototypes, all local: the grown-up app, the kids' app, the parent's Family controls, and two people sharing.

Summary

Notebook started as one person's notes and journal. It now has six sections (Notes, Journal, Finance, Links, the Agent and Documents), in a native SwiftUI app on both Mac and iPhone, and is moving from one person to a household:

  • Each adult has their own private notebook in their own iCloud, end-to-end encrypted, exactly as today.
  • Children get a friendlier Notebook whose apps and agent are set up by a parent from the parent's own devices. The rules are never shown to the child.
  • The agent is for getting things done for adults, and for curiosity for kids: space, science, history, math and nature, never homework.
  • People can share single items: notes and links collections that both can edit, and finance accounts the other person can only view.

The core design stays the same throughout: data lives on each device in SQLite as immutable revisions, syncs through CloudKit as ciphertext, and the same JavaScript logic runs on both platforms.

Principles worth keeping

  • Local first. Everything works offline. iCloud is a transport, never the source of truth.
  • Immutable revisions with parents. Wall clocks never pick a winner. Concurrent edits to prose keep both versions; Finance resolves deterministically so totals never double count.
  • Encrypt before upload. CloudKit stores AES-GCM ciphertext. Keys live in each device's keychain and move only through the QR pairing flow.
  • One logic, two platforms. Validation, agent tools, provider formats and Finance math are shared JavaScript. Only UI, HTTP and storage are platform code.
  • The agent is constrained in code. Read-only mode, protected fields, revision checks and forbidden keys are enforced by AgentCore.execute, not by instructions.

Design review findings

These come from reviewing the current code against the planned features. The first two must be fixed before sharing or family controls ship.

#FindingImpactRecommendation
1 HighRecordStore.insert accepts only today's seven record kinds and throws "Invalid sync revision" for anything else (RecordStore.swift:142). CloudSync then stops syncing.The first links, accountViews or family record would stop sync on every device that hasn't updated.Ship a release that stores unknown kinds without interpreting them and keeps syncing. Only then add new kinds.
2 HighCloudSync assumes one zone and one key: zoneID and key are single values, and every fetched record is opened with the notebook key.Sharing needs many zones, each with its own key, plus the shared database.Refactor to a zone-to-key routing table and a second sync engine for the shared database, with tests on isolated test containers, before any sharing UI.
3 HighBuilds are ad-hoc signed on the Mac and development-signed on iOS. CloudKit runs in the Development environment.Your partner, kids and other users can't install or sync reliably.TestFlight for iOS, Developer ID signing and notarization for the Mac, and the CloudKit schema deployed to Production with the new record types.
4 MediumOn the Mac, every store read or write starts a new helper process (execFileSync in native-store.js). The renderer also loads whole collections into memory.Attachments, links and shared items add more and larger calls; large PDFs pass through stdin each time.Keep one long-lived store process like the cloud process, and move search to SQLite as PERFORMANCE.md already suggests.
5 MediumAll revision history is kept forever, including media.Agent attachments (photos ~0.5 MB, PDFs up to 10 MB) will grow local storage and iCloud usage quickly.Add storage management: show attachment usage, let people remove old chat attachments, and compact superseded media revisions once every device has them.
6 MediumThere's no device revocation or key rotation.Family controls add more devices (kids') and need the family key rotated when a device is removed.Build key rotation once and use it for the notebook key, the family key and share keys.
7 LowThe app lock isn't disk encryption; the Mac SQLite file and Markdown files are readable by anyone who can log in to that macOS account.On a shared family Mac, a sibling could read another child's notebook.Recommend a separate macOS user per child, and say so in Family setup.
8 LowAgent attachments are stored under app_journalMedia_ keys, a journal-specific name.Confusing as media becomes general (notes, chat, links).Add a general app_media_ alias that reads and writes the same records.
9 LowThe app shell assumes a fixed set of sections (the AppManager comment still says two; menus use Cmd+1–4).Links needs a slot, and kid mode needs sections hidden by policy.Make sections a registry the policy can filter. Links becomes Cmd+4 and the Agent Cmd+5, or Links Cmd+5.
10 LowiOS bundles each shared JS file by name in the Xcode project.A new shared file (agent-policy.js, Links logic) silently missing on iOS fails only at runtime.Add a test that every file the iOS agent loads is in the project's resources.
